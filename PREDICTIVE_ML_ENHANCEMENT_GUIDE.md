# Predictive Maintenance ML + RUL Extension — Installation & Test Guide

## What is included
- `pdm_ml.py`: synthetic run-to-failure generator, trained binary failure-horizon classifier, RUL regressor, Isolation Forest anomaly model, SQLite persistence, deduplicated predictive WO and local alert queue.
- `pdm_stream.py`: simulated acquisition + online ML scoring every configured interval.
- `pdm_dashboard.py`: Streamlit trends, asset-level probability and RUL, notifications and production windows.
- Original `maintenance_engine.py`, `maintenance_ui.py`, `agent.py`, SOP knowledge files and original downtime RCA interface remain included.

## Install on Windows / VS Code
1. Extract into a **new folder**. Do not overwrite your existing working project without a backup.
2. Open `downtime_rca_agent` folder in VS Code.
3. In PowerShell:
   ```powershell
   py -3 -m venv .venv
   .\.venv\Scripts\Activate.ps1
   python -m pip install --upgrade pip
   pip install -r requirements.txt
   ```
4. Seed demo data (CAUTION: `--reset` deletes **maintenance_demo.db** and its maintenance transactions):
   ```powershell
   python seed_maintenance_demo.py --reset
   ```
5. Train models from 240 synthetic degradation episodes, with train/test split by episode to avoid row-wise leakage:
   ```powershell
   python pdm_ml.py train
   ```
6. Start dashboard:
   ```powershell
   streamlit run app.py
   ```
7. In another terminal start continuous simulated acquisition and scoring:
   ```powershell
   python pdm_stream.py --interval 3 --ticks 1000
   ```
8. Refresh Streamlit periodically to see latest results. The app does **not** auto-refresh by itself.

## Test scenarios
In the **Predictive & Preventive Maintenance Command Center** expand simulator controls and select an asset/scenario:
- `ASM-BRG-02` / `degrading`: gradually increasing vibration, warning and possible work order.
- `FRM-RECT-02` / `critical`: sustained overtemperature; check alert/WO and model scores.
- `ASM-SEN-03` / `sensor_fault`: intermittent anomalous measurements; check false-positive behavior.
- `ASM-MTR-01` / `normal`: stable baseline.
- `FRM-RECT-02` / `recovery`: reducing severity after intervention.
- Close a work order and issue a spare in the original dashboard to test stock/warranty tracking.
- Run the existing PM scheduler to test periodic preventive WOs.

### Trained models and features
- **Classifier**: HistGradientBoostingClassifier predicts simulated failure *within the next 12 acquisition cycles*.
- **RUL regressor**: RandomForestRegressor predicts remaining simulated acquisition cycles (capped at 120).
- **Anomaly detector**: IsolationForest produces an outlier score (lower = more anomalous).
- Features: normalized deviation, short-term slope, rolling volatility, alarm density, approximate observation age, mean deviation, alarm count.
- Training data are synthetic and generated by `make_training_data()` with 240 independent episodes. Evaluation splits by episode, not by individual readings.
- Outputs include held-out synthetic average precision, precision/recall at 0.5 and RUL MAE in ticks; see `models/training_metrics.json`.
- **Caution:** the classifier is trained on synthetic run-to-failure profiles, while live simulator scenarios use a different generator. Therefore the numerical probabilities and RUL are **not calibrated** or validated even for all demo scenarios, much less real equipment.

### Work orders, lead time and notifications
- Thresholds: HIGH if simulated probability >=0.65 or (RUL <=15 and anomaly score <-0.08); CRITICAL if probability >=0.85 or (RUL <=7 and anomalous). These are unvalidated demo values.
- When HIGH/CRITICAL, the system reuses an active predictive WO if one exists; otherwise creates an `ML_PREDICTIVE` WO, an alert and a **local SQLite** notification queue entry for the asset's team.
- Suggested production window is pulled from `production_windows` (seeded 12 hours ahead); it is **not** verified against MES schedules. The window is advisory, not an automatic assignment/approval.
- No real SMS, email, Teams, CMMS, SAP PM or PLC commands are sent.
- The stream interval is wall-clock seconds, but **RUL is measured in simulated acquisition cycles**, not validated physical operating hours. Changing `--interval` does not turn this into a trustworthy real-world lifetime estimate.
- Duplicate WO prevention works for an active `PREDICTIVE` or `ML_PREDICTIVE` WO; after closure, a persistent HIGH signal can create a new WO. Production logic needs cooldown/hysteresis and post-maintenance reset controls.

## Architecture
`PLC/MES/historian simulation -> SQLite readings -> rolling feature extraction -> IsolationForest + failure classifier + RUL regressor -> ML predictions -> alert + WO + local notification queue -> Streamlit dashboard`

## Production hardening checklist
1. Connect OPC UA/MQTT/historian in **read-only mode** with buffering, timestamp synchronization, units, quality flags and reconnect handling.
2. Capture verified failure dates, interventions, asset operating hours, censored runs and maintenance-reset events.
3. Train and validate **per failure mode / equipment family** with forward-in-time, site/asset-grouped holdouts; assess false alarms, alert lead time, calibration, precision-recall and RUL error.
4. Implement operational state (running/stopped), maintenance windows from MES, hysteresis/cooldown, authorization, deduplication, escalation, audit logs and work-order approval.
5. Connect email/Teams and CMMS/SAP PM through secured, authenticated adapters with retries and idempotency.
6. Monitor data/model drift and periodically retrain with governance and version control.
7. Do not rely on these synthetic predictions for actual maintenance or safety-critical decisions.
